# drawdown_signal — 드로다운 매수(물타기) 포워드 테스트

인기 종목 + Crypto + 지수 + 원자재 **28종목**을 매일 1회 훑어서, 52주 고점 대비 −30% 를
하향 돌파한 종목에 진입하고 −40 / −50% 에서 추가 체결(물타기)한 뒤
**실제로 수익률이 어떻게 되는지 원장에 기록**한다.

백테스트 원본: `backtest_quant/src/research/serve_drawdown_recovery.py`

---

## 왜 알림봇이 아니라 원장인가

"신호 떴다"만 보내면 포워드 테스트가 아니라 알림이다. 포워드 테스트가 되려면
**결과를 모르는 시점에 기록이 남아야** 한다. 그래서 진입가·기준고점·체결 이력을 박아두고,
실행될 때마다 열린 에피소드의 추가 MAE·물밑 일수·현재 수익을 갱신한다.

`backfilled` 플래그가 핵심이다. 원장이 생기기 전에 이미 시작된 에피소드는 사후 발견이지
실시간 포착이 아니다. 섞으면 포워드 테스트가 오염되므로 **모든 집계를 코호트로 분리**한다.

| 코호트 | 뜻 | 쓰임 |
|--------|-----|------|
| `out_of_sample` | 원장 생성 후 실시간 포착 | **판단의 본체** |
| `backfilled` | 원장 생성 시점에 이미 진행 중 | 참고용. 성과 주장에 쓰면 안 된다 |

## 규칙 (백테스트와 동일해야 의미가 있다)

```
진입   기준고점(252일 롤링) 대비 dd 가 −30% 하향 돌파
래더   −30% / −40% / −50% 3회 **등주수** 체결 → 수익률은 평단(avg_cost) 기준
청산   진입 시점 기준고점 회복
재진입 dd 가 −10% 위로 회복한 뒤에만 다음 에피소드 인정
보유일 상한 없음
```

두 번 어긋났던 곳 (둘 다 조용히 틀리는 종류):

1. **`auto_adjust=True`** 여야 한다. 백테스트가 수정주가를 쓴다. 원주가로 재면 배당 종목에서
   롤링 고점·dd 가 달라져 트리거 날짜 자체가 어긋난다.
   (IPO 분석에서는 반대로 `False` 가 맞았다 — 거긴 과거 계약가격과 비교하니까.)
2. **리셋 규칙**이 없으면 가격이 트리거 선을 넘나들 때 같은 하락을 여러 번 새 신호로 센다.

## 실행 경로

`main.py` lifespan 의 `_drawdown_scheduler` 가 **30분마다 폴링**하다가
`is_due()` 가 참이면 돌린다. cron 이 아니라 앱 안에 두는 이유:

- 배포 환경(Docker/Railway)에 호스트 crontab 이 없다.
- 컨테이너가 재시작돼도 원장의 `last_run` 을 보고 **catch-up** 하므로 하루 1회가 보장된다.

기본 실행 시각 `RUN_HOUR_UTC = 22` (= 07:00 KST, 미국장 마감 후·한국장 개장 전).

스케줄러와 대시보드의 수동 실행은 **같은 락**(`engine.run_exclusive`)을 공유한다.
원장이 단일 JSON 블롭이라 동시에 read-modify-write 하면 나중에 쓴 쪽이 앞의 결과를 통째로 덮는다.

## 원장 저장 위치

`DATABASE_URL` 이 있으면 **DB 가 정본**(`drawdown_ledger` 단일 행 JSON 블롭),
없으면 `data/drawdown_forward_ledger.json`.

Railway 컨테이너 파일시스템은 재배포마다 초기화된다. 파일에만 두면 배포할 때마다
`first_run` 이 되어 열린 에피소드가 전부 `backfilled` 로 다시 잡히고
**out-of-sample 기록이 영원히 0** 이 된다 — 포워드 테스트가 성립하지 않는다.

## 리소스 (실측 2026-07-28)

1회 스캔 = **7.5초 · yfinance 요청 28건 · 실패 0건**.
리플레이(롤링 고점·dd·래더·경로) 계산은 28종목 합쳐 **14ms** — 비용은 전부 네트워크 대기다.

| 항목 | 값 |
|------|-----|
| 일일 외부 요청 | 28건 (value_scan 은 641건/일 → 약 4%) |
| 스케줄러 폴링 | 48회/일, 각 회는 원장 1회 읽기뿐 |
| 대시보드 | **네트워크 0** — 원장만 읽고 120초 TTL 캐시 |
| 가격 시리즈 메모리 | 410KB (28종목 × ~890봉) |
| 프로세스 RSS 증가 | +32MB (pandas·yfinance, value_scan 이 이미 상주시킴) |

하루 1회라 사실상 무시할 수준. 병목이 생긴다면 종목 수가 아니라 yfinance 응답 지연 쪽이다.

## 대시보드 차트

`backtest_quant/posts/ipo-two-ways-in/chart.py` 의 **리서치 차트 문법**을 따른다.
소셜 카드와 문법이 반대다 — 작은 활자, 얇은 선, 높은 밀도, 범례 상자 대신 선 끝 직접 라벨,
구간별 표본 수 `n` 표기, 낮은 채도(`#2e6fd4` / `#8a5cd0`), 8:5 비율.

**보유 기간별 중앙값 수익률 곡선**이 핵심이다. 같은 신호를 두 방식으로 재서 겹쳐 그린다:

```
single  1차 진입가에 1주만          → last / entry_price - 1
ladder  −30/−40/−50% 등주수 3회     → last / avg_cost    - 1
```

두 선 사이 간격이 물타기 프리미엄이다. 주의할 점 두 가지를 차트가 직접 말하게 해뒀다:

- **투입 자본이 다르다.** ladder 는 Σp, single 은 p₀ 를 쓴다. ROI 가 같아도 절대 손익·리스크
  노출은 ladder 쪽이 크다 → `capital_units`(Σp/p₀) 를 항상 같이 띄운다.
- **미래 체결 소급 금지.** 각 구간의 평단은 **그 시점까지 체결된 것만** 반영한다
  (`engine._return_path`). 전체 평단을 +5일 지점에 적용하면 물타기가 실제보다 좋아 보인다.

곡선 모수는 **에피소드 전체**(체결 1회 포함)다 — 실제로 이 전략을 돌렸을 때 받는 곡선이라서다.
반면 `stats.ladder` 비교 패널은 **체결 2회 이상만** 쓴다 (1회면 두 전략이 같아 평균이 희석된다).
